# Design

## Context

The documentation site is Sphinx 9 with MyST, furo, `sphinx-design`, and `sphinx-copybutton`. It
builds with `-W --keep-going` and `nitpicky=True` in both `ci.yml` and `docs.yml`. There are 27
Markdown pages: one landing page, one quickstart, nine guides, ten reference pages, and six
generated API pages.

`tests/test_docs_examples.py` executes every Python fence in the landing page, quickstart, and
guides, and parses every Python fence in the reference and API pages. Its regex only matches
`python` fences, so diagram fences are unaffected.

No page currently uses a callout, a diagram, or a style guide; `docs/_static/custom.css` only
styles cards. The docs workflows install Python only. Node 24 is available in the development
environment, but neither `mmdc` nor Chromium is installed.

See `proposal.md` for motivation and `specs/documentation-style/spec.md` for the behavior contract.

## Goals / Non-Goals

**Goals:**

- A warm teaching layer on the landing page, quickstart, and guides without changing the reference's
  authority.
- One visual language for summaries, tips, warnings, remembered rules, and optional depth.
- Every graph example shown visually before its code.
- Diagrams that render offline, need no client-side runtime, and fail the build when malformed.
- A published style guide that humans and future apply runs can follow.

**Non-Goals:**

- Dark-mode-aware diagram colours or a theme-toggle re-render.
- Mermaid in `README.md` (PyPI does not execute it).
- Rewriting reference content, grammar, or the conformance matrix.
- Generating diagrams from source code or validating diagram names against snippets automatically.
- Any runtime dependency, public API, CLI, or data-format change.

## Decisions

### Three voice zones

| Zone | Pages | Voice |
| --- | --- | --- |
| Warm | `index.md`, `getting-started/quickstart.md`, `guides/*.md` | Second person, outcome first, short paragraphs, diagrams and callouts |
| Precise | `reference/*.md` | Rules, edge cases, canonical spellings; summaries and semantic diagrams only |
| Generated | `api/*.md` | Autodoc listings; no `tl;dr`, no emoji, no callouts |

The boundary is a page rule, not a per-paragraph judgement. A warm page may link to the reference
for exact behavior; a reference page may use a diagram when it encodes semantics, but never adopts
the guide voice.

### Five callout types

Use MyST's built-in admonitions and retitle two of them with a CSS class. No custom directive.

| Type | Purpose | Markup | Rendering |
| --- | --- | --- | --- |
| `tl;dr` | Page outcome in at most three sentences | `:::{admonition} tl;dr` + `:class: tldr` | Brand-coloured box, custom icon |
| `Tip` | Optional shortcut or nicer way | `:::{tip}` | furo green tip with info icon |
| `Warning` | Data loss, wrong result, or footgun | `:::{warning}` | furo orange warning with warning icon |
| `Remember` | The one rule to carry away | `:::{admonition} Remember` + `:class: important` | furo teal "important" styling, flame icon |
| `In detail` | Optional technical depth; safe to skip | `:::{admonition} In detail` + `:class: detail` | Neutral styling, pencil icon |

`custom.css` adds `.tldr` and `.detail` rules and reuses furo's CSS custom properties so both
themes keep readable contrast. The title is fixed by convention and enforced by a structural test;
no page may retitle a block ("Note:", "Heads up!", and so on).

**Alternative considered:** a custom `{tldr}` directive. Rejected for now because it puts Python
under `docs/`, which Ruff and Pyrefly do not check (`src = ["src", "tests", "examples"]`), and the
plain admonition already produces the same output. The directive remains a clean upgrade if the
markup proves too noisy.

**Alternative considered:** `{sidebar} tl;dr` for a real margin-note feel. Rejected as the default
because a 30%-wide float is a poor fit for a page summary; the sidebar stays available for optional
asides later.

### Page summaries

A `tl;dr` callout appears immediately after the H1 on every page except `api/*.md`. It is at most
three sentences, states the outcome, and introduces no claim the page does not support. The page's
H1 remains the title; the callout is not a heading, so it does not affect anchors or the toctree.

The preview generated by the landing page and quickstart is the pattern setter: a reader should be
able to stop after the callout and still know whether the page is for them.

### Emoji at level 3, with all-or-nothing consistency

Emoji are allowed in card titles and badges. They are forbidden in headings, body prose, callout
titles, and diagrams. A card grid either gives every card an emoji or gives none an emoji; a badge
collection follows the same rule.

Headings stay emoji-free for a concrete reason: MyST derives anchors from heading text, and emoji
are not word characters. `🚀 Install` becomes `#-install`, which pollutes anchors, the toctree, and
screen-reader output. Keeping headings plain avoids the problem entirely.

Badges are limited to the guide landing cards: one reading-time badge and one level badge per card.
No page-level badges, no badges in the reference.

### Graph examples begin with a diagram

Every example that introduces a graph shape gets a diagram before the first snippet. The diagram
uses exactly the node names, labels, property names, and relationship types in the code. Later
snippets that vary only a filter or property reuse the diagram by reference.

Diagram types are limited to `flowchart` and `stateDiagram-v2`; the style guide records the list.
Rough inventory:

| Page | Diagram |
| --- | --- |
| `index.md` | one SQLite file holding nodes, labels, properties, relationships |
| `getting-started/quickstart.md` | the reader's path; the Kevin/Quorra example graph |
| `guides/examples.md` | the grid, cast, and places datasets and how they link |
| `guides/querying.md` | match, optional match, and aggregation shapes |
| `guides/indexes.md` | the lookup the planner chooses |
| `guides/constraints.md` | a uniqueness violation before and after |
| `guides/importing.md` | JSONL to graph pipeline |
| `guides/interop.md` | export and import round trip |
| `guides/shell.md` | one shell session |
| `guides/embedding.md` | connection and transaction lifecycle |
| `reference/query-language.md` | path vs. walk vs. trail; variable-length expansion |
| `reference/gql-profile.md` | the five profile tiers |
| `reference/index-behavior.md` | planner choice |
| `reference/snapshot-format.md` | file layout |

A diagram earns its place only when it replaces prose or disambiguates a shape that the code alone
makes hard to see; decoration is cut. Before page work, an example inventory records a
diagram-or-prose decision for every example group in the landing page, quickstart, and guides, and
marks prose-only examples explicitly. One diagram per distinct shape, never two diagrams in a row.

### Pre-rendered SVG, not client-side Mermaid

Use `sphinxcontrib-mermaid` with `mermaid_output_format = "svg"`. At build time the extension calls
`mmdc`, the Mermaid CLI, and writes a content-hashed `.svg` into `_images`. The page embeds it with
an `<object>` element. There is no Mermaid JavaScript, no CDN, and no runtime parsing.

```python
extensions = [..., "sphinxcontrib.mermaid"]

mermaid_output_format = "svg"
mermaid_cmd = "npx --yes @mermaid-js/mermaid-cli@<pinned>"
mermaid_config = {
    "theme": "neutral",
    "themeVariables": {
        "background": "#f8f9fb",
        "fontFamily": "ui-sans-serif, system-ui, sans-serif",
    },
}
mermaid_params = ["--puppeteerConfigFile", "docs/puppeteer-config.json"]
```

`docs/puppeteer-config.json` holds `{"args": ["--no-sandbox"]}` for headless Chromium in CI.

**Why this over raw client-side rendering:** the build itself parses and validates every diagram, so
a malformed diagram fails `sphinx-build -W` instead of surfacing as a red box after deploy. The
output is self-contained, printable, and works offline. Since dark mode is out of scope, fixed
colours are acceptable.

**Alternative considered:** raw client-side rendering plus a separate `mmdc` CI job. Rejected
because it needs two rendering paths, two version pins, and the browser still parses at read time.

**Alternative considered:** pre-render to committed SVG files. Rejected because it creates a
generated-artifact workflow and a staleness check, while still requiring Node to author diagrams.

### Authoring form

Use the `{mermaid}` directive fence, not a bare ` ```mermaid ` fence:

```markdown
```{mermaid}
:alt: Kevin Flynn has an ALLIES_WITH relationship to Quorra.

flowchart LR
  K["Kevin Flynn<br/>Program, User"] -->|ALLIES_WITH| Q["Quorra<br/>Program, ISO"]
  accTitle: Kevin Flynn allies with Quorra
  accDescr: A directed relationship from Kevin Flynn to Quorra.
```
```

The directive form allows `:alt:` for the `<object>` fallback and leaves room for `:caption:`.
A bare fence would need `myst_fence_as_directive = ["mermaid"]` and would lose both options; the
gain would be GitHub previews of `docs/*.md`, which is not the primary reading surface.

### Diagram typography

The base diagram font is Inter; entity names stay sans-serif. Labels, relationship types, property
keys, values, and syntax are wrapped in `<code>` and render in JetBrains Mono. Both fonts are
bundled under the SIL Open Font License 1.1 in `docs/_static/fonts/`, and the same faces are used by
the HTML site. Mermaid strips `@font-face` from `themeCSS`, so the `build-finished` hook injects the
font-face rules into every rendered SVG; the URLs are relative to `_images` and resolve to
`_static/fonts/`.

**Cache gotcha:** the extension hashes the diagram code and directive options, and `mermaid_config`
is injected into the code, so theme changes invalidate the cached SVG. `mermaid_params` is not in
the hash; changing it alone silently reuses old files. Keep visual settings in `mermaid_config` and
delete `_build/html/_images` if `mermaid_params` changes.

### Build gate and structural tests

A malformed diagram raises `MermaidError`, which the extension logs as a warning; `-W` turns that
into a failed build. No separate validation job is needed. When `mmdc` is missing, the extension
also warns, so a missing tool fails the build with an actionable message.

`tests/test_docs_style.py` covers what the parser cannot: `tl;dr` presence on non-API pages, the
five-callout vocabulary, all-or-nothing emoji in card grids, and `accTitle`/`accDescr` presence on
every diagram. These are structural checks, not prose-quality checks.

### Published style guide

`docs/contributing/documentation-style.md` is the canonical human guide. It renders each of the
five callouts, shows a before/after rewrite, states the emoji and badge rules, defines the diagram
conventions, and ends with a short checklist. It is reachable from a new "Contributing" toctree
caption.

`AGENTS.md` gains a compact "Documentation voice" section that states the non-negotiables and links
to the page, plus the Node/Mermaid CLI prerequisite for `hatch run docs:build`. The hard rules live
in `AGENTS.md` because apply runs read it; the full prose lives on the page to avoid drift from a
second copy.

### CI wiring

Both `ci.yml` and `docs.yml` add `actions/setup-node` and cache `~/.npm` and `~/.cache/puppeteer`,
keyed by the pinned CLI version. The first run downloads Chromium; later runs reuse it. The docs
deploy already depends on the build, so a broken diagram blocks publishing.

`pyproject.toml` adds `sphinxcontrib-mermaid` to the `docs` extra, and `CHANGELOG.md` records the
new documentation experience and toolchain.

## Risks / Trade-offs

- **Every docs build needs Node and Chromium.** → Document the prerequisite in `AGENTS.md`, pin the
  CLI, cache the browser in CI, and let the build fail with the extension's actionable missing-command
  warning.
- **A clean build is slower.** → Content-hashed filenames in `_images` make incremental builds skip
  unchanged diagrams; CI caches the npm and Puppeteer downloads.
- **Wide SVGs can overflow the content column.** → Add an `article object[type="image/svg+xml"]`
  rule with `max-width: 100%`, centring, and block display; check the widest diagrams visually.
- **Diagram text is not part of the page's searchable prose.** → Put the meaning in the surrounding
  paragraph, use `:alt:`, `accTitle`, and `accDescr`, and never make a diagram the only explanation.
- **Font metrics can differ between CI and the reader.** → Pin `fontFamily` in `themeVariables` and
  keep diagrams small enough that small differences do not change the layout.
- **Diagrams can drift from the code they illustrate.** → Require identical names in the style
  guide and review diagrams alongside snippets; the parser cannot check this.
- **Emoji can hurt tone and accessibility if overused.** → Restrict them to cards and badges, keep
  them out of headings and prose, and require all-or-nothing within a collection.
- **`tl;dr` boxes can drift from the page body.** → Cap them at three sentences and review them in
  the same pass as the page update.
- **`mmdc` and Mermaid versions can drift if unpinned.** → Pin the CLI version in `conf.py` and use
  that version in the CI cache key.
- **Dark mode shows light diagram cards.** → Accepted for this change; the neutral theme with an
  explicit light background stays legible in both modes.

## Migration Plan

1. Foundation: add the extension and dependency, the five callout styles, `puppeteer-config.json`,
   the style guide page, the `AGENTS.md` rules, and CI Node setup.
2. Prove the pattern on the landing page and quickstart.
3. Apply the pattern to the nine guides, starting with `examples.md` and `querying.md`.
4. Apply summaries and semantic diagrams to the ten reference pages.
5. Add the cross-page structural tests, then run `hatch run docs:build`, `hatch check --fix`, and
   `hatch test`; verify the deploy workflow is green.

Rollback is a documentation revert: remove the dependency, extension, styles, Node steps, and
diagram fences. There is no data migration and no runtime impact.
